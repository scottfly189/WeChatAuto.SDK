    WeChatDatabaseInfo

    WeChatMessage

    微信消息中间表。UIA 监听与 Database Read 共用；支持多微信聚合。 对照原生 message_0/1/2.db 的 Msg_（各表同构）：差异同步业务键为 FromWechatWxId + ChatUsername + Shard + LocalId（ServerId 作辅助，不建外键）。 本机有 89 个会话跨 message_0/1/2，且各分片 local_id 都从 1 计，业务键必须带 Shard。 增量水位用 SortSeq：跨分片区间不重叠，按 FromWechatWxId + ChatUsername + Shard 取 MAX(SortSeq) 即可。 server_id / sort_seq / local_type 等会超过 Int32，C# 用 long 承接； 列类型显式声明 INTEGER（SQLite 的 INTEGER 最多 8 字节，可存 64 位）。 不要改成 C# int，也不要让 SqlSugar 默认映射成 BIGINT。 自增主键仍必须是 int：SqlSugar 把 long 主键映成 BIGINT，SQLite 不允许 AUTOINCREMENT。 UIA 写入时这些原生键可为空或 0，故先不加唯一约束，避免和旧行冲突。 发送者 username 在本分片 Name2Id.rowid = real_sender_id 解析后写入 SenderWxId， 不要跨分片使用 rowid。message_content 若被 WCDB 标成 zstd，写入前先解码； 群聊正文常见「sender_wxid:\n正文」，发送者进 SenderWxId，正文进 Content。 引用消息（local_type=244813135921）Content 只存回复文字，被引用内容在 Quote 列。 packed_info_data / source / compress_content 不镜像进本表。

    WeChatSnsComment

    朋友圈评论中间表。完整名单来自 SnsTimeLine.content XML 的 comment_user_list（条目 type 一律为 2）。 同一条若在 SnsMessage_tmp3.serialized_comment_buf 有包，重叠字段 （发起人、对象、类型、时间、正文、comment_id、flag）以 protobuf 为准；名单本身不在包里，仍以 XML 列表为准。 回复的父评：serialized_ref_buf 为完整包时，父评正文与发起人优先用包；否则用 XML 的 ref_comment_id / ref_username。

    WeChatSnsLike

    朋友圈点赞中间表。完整名单来自 SnsTimeLine.content XML 的 like_user_list（条目 type 一律为 1）。 同一条若在 SnsMessage_tmp3.serialized_comment_buf 有包，重叠字段 （发起人、昵称、时间、comment_id、flag）以 protobuf 为准；名单本身不在包里，仍以 XML 列表为准。

    WeChatSnsMedia

    朋友圈媒体中间表：一条动态可以有多张图 / 多个视频（含 LivePhoto 的视频段）。 数据来自 SnsTimeLine.content 的 ContentObject/mediaList/media，按 (Tid, Idx) 唯一。

    URL 是带 token 的 CDN 地址，会过期；LocalPath 预留给后续的媒体下载/缓存。

    视频号（finderFeed）的媒体列表结构与朋友圈 media 不同，暂不写入本表，见 FinderKind / FinderId。

    WeChatSnsPost

    朋友圈动态中间表，对应原生 SnsTimeLine（按 tid）。支持多微信聚合。 正文、媒体、类型、点赞标记、发布时间主要来自 content XML（SnsDataItem / TimelineObject）。 pack_info_buf 是 protobuf，可以读，但本机绝大多数是空包，有值时只重复 tid 与时间， 不含正文或互动名单；CreateTime 以 XML <createTime> 为准，包内 field 2 有值时作校对。 完整点赞 / 评论不进本表，分别写入 WeChatSnsLike / WeChatSnsComment。
