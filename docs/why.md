# 为什么选择 WeChatAuto.SDK


## 一句话答案

> **纯数据库工具强在“读”，纯界面自动化工具强在“写”；我们把两条路合起来——读微信数据走数据库路线（不碰微信原生数据库，而是先镜像到旁路/其他目录，在旁路进行读取），写操作走UI自动化，中间用热同步和中间表把多微信数据做聚合。**


---

## 与现有解决方案对比:

| 你关心的 | 纯数据库类(weflow\wechatauto-replica等) | 纯界面自动化类(wxauto等) | 我们 |
|---|---|---|---|
| 读历史消息 | 快、全 | 慢，要滚动，容易漏 | **热同步/旁路读取** |
| 发消息、加好友、发朋友圈 | 绝大多数做不了 | 能做 | **能做** |
| 多个微信 | 各自解密、各自维护 | 容易互相干扰 | **一套中间表聚合；多微信号同时服务** |
| 首次使用 | 要找目录、取密钥 | 要开微信、调窗口 | **自动发现，基本零配置** |
| 对用户的打扰 | 不占界面，但取密钥有风险 | 抢鼠标键盘、抢焦点 | **读数据零打扰；写操作可控/安全** |
| 微信升级 | 密钥一失效就全线不可用 | 部分动作失效 | **分层适配，影响面小** |
| 对接自己的系统 | 要自己解析微信表 | 要自己写界面脚本 | **容易 - 标准数据库，可直接写 SQL或通过API调用** |
| 整合难度 | 大多为成品，做自己的应用要剔除多余部分 | 不带UI | **容易 - 以纯SDK为底层，也提供最精简的吸附条UI** |

> 社区版相当于“纯界面自动化”这一列，但把稳定性、多实例和工程化做得更完整；VIP 才是“读 + 写”的混合方案。

---

## 我们怎么做：两条链路

```text
业务系统 / 客户应用
        │
        ├── 读链路
        │     微信本地数据库 → 热同步 / 安全直读 → 中间表 → 业务系统
        │
        └── 写链路
              业务系统 → SDK → UI自动化 → 操作微信客户端
```

- **读链路**不打开聊天窗口、不抢键鼠，适合历史数据/大库、批量查询、实时增量；
- **写链路**负责发消息、加好友、发朋友圈、群操作这些必须“动手”的动作；
- 两条链路互不阻塞：读数据不经过界面，写操作不等待读任务。

## 我们的六个特色

1. **启动基本零配置**
   自动发现微信窗口和账号，客户不用自己翻目录、填路径；VIP 还会自动发现数据库位置，密钥首次获取后自动缓存。

2. **后台热同步，数据持续更新（VIP）**
   在后台把新消息、联系人、群成员、朋友圈持续搬到中间库，只同步变化的部分，不反复全量，长期运行也稳。

3. **读消息不抢鼠标键盘（VIP）**
   读数据不需要打开聊天窗口、不占键鼠、不卡微信界面；历史消息再多也能批量读，适合做数据平台、客服系统、归档系统。

4. **多个微信，一套表（VIP）**
   多个微信的数据统一进中间表，支持 SQLite、SQL Server、MySQL、PostgreSQL 等标准数据库；业务方直接写 SQL，不用理解微信原始表结构。

5. **读->用数据库解决方案，写->用UI自动化**
   发消息、加好友、发朋友圈这类必须“动手”的动作，走我们最擅长的界面自动化；能读库的绝不点界面，既快又不打扰用户。

6. **多微信并行，敏感操作不打架**
   多个微信可以同时在线、同时被服务；界面动作统一调度、按账号排队执行，不会因为一个号在操作，另一个号就失败。

## 明确的安全边界

| 我们做 | 我们不做 |
|---|---|
| 通过界面自动化操作真实微信 | 不向微信进程注入第三方模块 |
| 通过 OCR / 无障碍树识别界面 | 不 Hook 微信消息、不破解通信协议 |
| VIP 只读微信数据库，不写回原库 | 不注入式改库、不篡改聊天记录 |
| 支持硬件级键鼠模拟，降低软件模拟痕迹 | 不承诺“绝对不被风控” |

> **强开 UI Tree** 是启动阶段的兼容处理，用于让微信暴露无障碍树；业务数据读写始终不经过它，也不会修改聊天记录。
>
> 安全是工程问题，不是一句“零风险”的承诺；我们尽量把风险控制在**正常使用微信**的范围内。

## 适合谁，不适合谁

### 适合

- 要把微信消息接入自己的 CRM、客服系统、工单系统或 AI Agent；
- 需要多账号聚合、消息持久化、按会话/时间/关键词查询；
- 需要按 WxId 精准发送消息、文件、表情、语音；
- 希望先用社区版验证业务，再按需升级 VIP 数据能力；
- 能接受“界面自动化需要跟随微信版本维护控件”的工程团队。

### 不适合

- 想绕过微信安全机制、批量骚扰、恶意营销；
- 要求“永不封号”“完全零风险”的场景；
- 不愿意做任何版本适配和运行环境维护；
- 违法违规用途。

## 能力分层：从“能操作”到“能查询”

| 层级 | 能力 | 版本 |
|---|---|---|
| **操作层** | 发送消息/文件/表情/语音、好友、群、窗口、导航 | 社区版 + VIP |
| **监听层** | 新消息、好友申请、群系统消息、轮询拉取 | 社区版 + VIP |
| **数据层** | 多账号联系人/消息/群成员/朋友圈同步到自己的数据库 | VIP |
| **查询层** | 按会话、时间、关键词、联系人、群、朋友圈查询；自定义查询 | VIP |
| **精准操作层** | 按 WxId 发送文字/文件/表情/语音 | VIP |

> 社区版解决“先把微信操作跑起来”；VIP 解决“把微信数据变成可查询、可同步、可精准操作的业务数据”。

### VIP 的四个核心价值

| 核心价值 | 解决的问题 | 落地能力 |
|---|---|---|
| **大库同步** | 历史消息多、首轮同步慢、整库拷贝占用大 | 增量同步到自己的数据库，不把微信原库当业务库 |
| **多账号聚合** | 多个微信账号数据分散，业务要逐个窗口处理 | 同一套中间库按账号区分，统一查询 |
| **消息持久化** | 消息只在微信里，无法稳定查询、统计、追溯 | 消息、联系人、群成员、朋友圈落库，可按会话/时间/关键词查询 |
| **按 WxId 精准发送与查询** | 昵称会变、会重名，按昵称操作不稳定 | 用 WxId 定位联系人和会话，精准发送、精准查询 |

## 稳定上生产的工程细节

### 界面操作统一排队

微信界面自动化里，监听任务和发送任务如果并行操作界面，会互相打断；多微信同时在线时尤其明显。

WeChatAuto.SDK 对需要走界面的操作做了统一排队：

- **一条专用线程**：无论开了几个微信，所有界面操作统一调度到同一条专用线程串行执行；
- **监听统一排队**：所有自动监听任务受同一把信号量约束，与发送操作互斥、顺序执行。

VIP 的数据读取走 Safe Database Read，不再靠在界面上逐条抓消息；界面线程只负责必须“点”的操作。

### 强开 UI Tree：微信不公开 UI Tree 也能自动化

微信默认并不公开 UI Tree，常规界面自动化方案在拿不到 UI Tree 时会直接失效。WeChatAuto.SDK 内置“强开 UI Tree”能力：

- 定位 `weixin.dll` 中的门控字节并写入，让微信暴露 UI Tree；
- 过程中有可视化进度提示，状态清晰可见。

**效果**：不依赖微信是否“开放”，兼容性更强；即使某个微信版本改了控件，也只是维护界面定位，而不是重做整套逆向方案。

更多说明见 [如果没有 UI Tree 怎么办](https://github.com/scottfly189/WeChatAuto.SDK/issues/3)。

### 远程桌面支持

界面自动化最怕远程桌面：RDP 窗口最小化或断开时会挂起远端显示缓冲，导致自动化拿不到画面、投不进输入。WeChatAuto.SDK 做了针对性适配：

- **禁用 RDP 最小化挂起优化**，最小化远程桌面也不中断自动化；
- **会话转移**：支持把 RDP 会话转回控制台会话，关掉远程桌面后会话仍保持解锁；
- **自动恢复分辨率**：避免会话转移后回落成 1024×768 导致图像识别、坐标定位失败。

**效果**：可以最小化远程桌面、关闭远程桌面客户端，而不用担心“人一断开，机器人就停了”。

## 为 AI Agent / 多语言接入而生

- **事件驱动**：好友申请、新消息监听通过回调 / Channel 推给你，天然适合接 LLM 做自动应答。
- **语音交互**：支持文字转语音发送；VIP 提供声音复刻，语音 Agent 开箱即用。
- **多语言客户端**：除 .NET 外，还提供 C++ / Go / Java / Node.js / Python / Rust 官方客户端，任何技术栈都能接。
- **数据可查询**：VIP 的 Safe Database Read 让 Agent 能按会话、时间、联系人、关键词取数，而不是只靠界面抓取。

## 两种使用方式，按需接入

| | 内嵌方式 | HTTP WebAPI 方式 |
|---|---|---|
| 适合 | .NET / Windows 原生应用，需要事件回调、低延迟、完整 API | 后端/云服务、跨语言、多系统共享、快速集成 |
| 入口 | `WeAutomation.Initialize(...)` → `WeChatClientFactory` → `WeChatClient` | 启动 Server，REST + Swagger，`http://<主机>:5000` |
| 特点 | 类型安全、能力最全、深度定制 | 语言无关、进程隔离、可远程、开箱即用 |

> 绝大多数场景推荐 HTTP WebAPI 方式；需要 DLL 内嵌、深度回调时选内嵌方式。

## 快速开始（30 秒上手）

### 内嵌方式（.NET）

```bash
dotnet add package WeChatAuto4x.SDK
```

```csharp
var sp = WeAutomation.Initialize(o => o.EnableOCR = true);
using var factory = sp.GetRequiredService<WeChatClientFactory>();
var client = factory.GetWeChatClient("你的微信名");
await client.SendMessage("好友昵称", "hello world!");
```

### HTTP WebAPI 方式

```bash
# 启动 Server 后，任何语言都能调用
curl http://localhost:5000/api/v1/clients

curl -X POST http://localhost:5000/api/v1/clients/<clientId>/messages/send \
  -H "Content-Type: application/json" \
  -d '{"who": "好友昵称", "message": "你好"}'
```

更多接口与字段见 [HTTP 服务使用说明](httpserveruse.md) 与 [中间表字段说明](schema.md)。
