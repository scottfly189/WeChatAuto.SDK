
# 为什么选择 WeChatAuto.SDK

## 一句话定位

> **不注入、不破解协议、不写回微信数据库。**  
> WeChatAuto.SDK 是面向开发者的微信自动化开发包，帮助你构建自己的微信机器人、微信助手和 AI Agent。

本仓库是 **社区开源版**：用 **UI Automation + OCR** 操作真实微信，可以先跑通监听、发送、好友、群等基础能力；需要把微信数据变成可查询、可同步的业务数据时，再升级到 VIP 的 **Safe Database Read**。

**关键词：** UI 自动化 · 多账号 · 事件监听 · 数据查询 · 可上生产

---

## 30 秒结论

- **想快速接入**：社区版用 UI Automation，不碰微信数据库，先跑通发送、监听、好友和群管理。
- **要把消息变成业务数据**：VIP 提供 Safe Database Read，把多账号联系人、消息、群成员、朋友圈同步到自己的数据库。
- **要稳定上生产**：统一 UI 操作队列、多实例支持、远程桌面适配、硬件级键鼠模拟，按工程化方式交付。
- **不想承担逆向维护成本**：不 Hook 消息、不破解协议、不注入第三方模块进微信进程。

完整能力对照见 [WECHATAUTO.SDK 能力矩阵](ability.md)。

## 微信自动化的三个老大难

| 痛点 | 传统做法的代价 |
|---|---|
| **安全与合规** | 内存 Hook、协议破解、注入式改库，容易触发微信风控，且处于灰色地带 |
| **易碎难维护** | 微信一升级，Hook 点、协议、控件路径全部失效，需要持续逆向跟进 |
| **上手门槛高** | 逆向工程、协议分析、控件定位繁琐，业务团队难以快速落地 |

WeChatAuto.SDK 选择的是另一条路：**在真实微信界面上做自动化，把“像人操作”作为第一原则。**

我们不承诺“零风控”，但尽量把风险控制在**正常使用微信**的范围内：不注入、不破解协议、不写回微信数据库。

---

## 我们选择的技术路线

### 1. UI Automation，而不是 Hook / 协议破解

社区版通过 Windows UI Automation 操作真实微信窗口：

- 发送消息、文件、表情、语音；
- 监听新消息、好友申请、群系统消息；
- 管理好友、群聊、通讯录、窗口和导航；
- 配合 OCR 处理 UI Tree 拿不到的场景。

这条路的好处是**可解释、可调试、可维护**：微信升级后通常只需要调整控件定位，而不是重做一套逆向方案。

### 2. 双路径：UIA 负责“操作”，Safe Database Read 负责“数据”

| 路径 | 负责什么 | 适合 |
|---|---|---|
| **UI Automation** | 发送、监听、好友、群、窗口等必须“点界面”的操作 | 社区版；VIP 也继续使用 |
| **Safe Database Read** | 把联系人、消息、群成员、朋友圈同步到自己的数据库，或直接查询微信加密库 | VIP；大库、多账号、数据型业务 |

两者不是互相替代，而是分工：

- **要“操作微信”** → UI Automation；
- **要“读取和分析微信数据”** → Safe Database Read。

> Safe Database Read 不注入微信进程、不修改微信原数据；它和“注入式改库 / 协议破解”不是同一条路。

### 3. 明确的安全边界

我们尽量把“能做什么、不做什么”说清楚：

| 我们做 | 我们不做 |
|---|---|
| 通过 UI Automation 操作真实微信 | 不向微信进程注入第三方模块 |
| 通过 OCR / 无障碍树识别界面 | 不 Hook 微信消息、不破解通信协议 |
| VIP 只读微信数据库，不写回原库 | 不注入式改库、不篡改聊天记录 |
| 支持硬件级键鼠模拟，降低软件模拟痕迹 | 不承诺“绝对不被风控” |

> **强开 UI Tree** 是启动阶段的兼容处理，用于让微信暴露无障碍树；业务数据读写始终不经过它，也不会修改聊天记录。

## 适合谁，不适合谁

### 适合

- 要把微信消息接入自己的 CRM、客服系统、工单系统或 AI Agent；
- 需要多账号聚合、消息持久化、按会话/时间/关键词查询；
- 需要按 WxId 精准发送消息、文件、表情、语音；
- 希望先用社区版验证业务，再按需升级 VIP 数据能力；
- 能接受“UI 自动化需要跟随微信版本维护控件”的工程团队。

### 不适合

- 想绕过微信安全机制、批量骚扰、恶意营销；
- 要求“永不封号”“完全零风险”的场景；
- 不愿意做任何版本适配和运行环境维护；
- 违法违规用途。

| 层级 | 能力 | 版本 |
|---|---|---|

## 工程化打磨：为“稳定上生产”而生

### 界面操作统一排队

微信 UI 自动化里，**监听任务**和**发送任务**如果并行操作界面，会互相打断；多微信同时在线、单微信群发时尤其明显。

WeChatAuto.SDK 对需要走界面的操作做了统一排队：

- **一条专用 Action 线程**：无论开了几个微信，所有 UI 操作统一调度到同一条专用线程串行执行；
- **监听统一排队**：所有自动监听任务受同一把信号量约束，与发送操作互斥、顺序执行。

VIP 的数据读取走 Safe Database Read，不再靠在界面上逐条抓消息；界面线程只负责必须“点”的操作。

### 强开 UI Tree：微信不公开 UI Tree 也能自动化

微信默认并不公开 UI Tree，常规 UI 自动化方案在拿不到 UI Tree 时会直接失效。WeChatAuto.SDK 内置“强开 UI Tree”能力：

- 定位 `weixin.dll` 中的门控字节并写入，让微信暴露 UI Tree；
- 过程中有可视化进度提示，状态清晰可见。

**效果**：不依赖微信是否“开放”，兼容性更强；即使某个微信版本改了控件，也只是维护 UI 定位，而不是重做整套逆向方案。

更多说明见 [如果没有 UI Tree 怎么办](https://github.com/scottfly189/WeChatAuto.SDK/issues/3)。

### 远程桌面支持：云服务器 / RDP 上稳定运行

UI 自动化最怕远程桌面：RDP 窗口最小化或断开时会挂起远端显示缓冲，导致自动化拿不到画面、投不进输入。WeChatAuto.SDK 做了针对性适配：

- **禁用 RDP 最小化挂起优化**，最小化远程桌面也不中断自动化；
- **会话转移**：支持把 RDP 会话转回控制台会话，关掉远程桌面后会话仍保持解锁；
- **自动恢复分辨率**：避免会话转移后回落成 1024×768 导致图像识别、坐标定位失败。

**效果**：可以最小化远程桌面、关闭远程桌面客户端，而不用担心“人一断开，机器人就停了”。

## 为 AI Agent / LLM 时代而生

- **事件驱动**：好友申请、新消息监听通过回调 / Channel 推给你，天然适合接 LLM 做自动应答。
- **语音交互**：支持文字转语音发送；VIP 提供声音复刻，语音 Agent 开箱即用。
- **多语言开放**：核心库之外，提供 7 个语言的官方客户端（.NET / C++ / Go / Java / Node.js / Python / Rust），任何技术栈都能接。
- **数据可查询**：VIP 的 Safe Database Read 让 Agent 能按会话、时间、联系人、关键词取数，而不是只靠界面抓取。

## 两种使用方式，按需接入

| | 内嵌方式 | HTTP WebAPI 方式 |
|---|---|---|
| 适合 | .NET / Windows 原生应用，需要事件回调、低延迟、完整 API | 后端/云服务、跨语言、多系统共享、快速集成 |
| 入口 | `WeAutomation.Initialize(...)` → `WeChatClientFactory` → `WeChatClient` | 启动 Server，REST + Swagger，`http://<主机>:5000` |
| 特点 | 类型安全、能力最全、深度定制 | 语言无关、进程隔离、可远程、开箱即用 |

> 绝大多数场景推荐 HTTP WebAPI 方式；需要 DLL 内嵌、深度回调时选内嵌方式。

## 安全与风控：把“像人”做到硬件级

高频自动化的风险主要来自微信风控。WeChatAuto.SDK 除了软件模拟，还支持**硬件级键鼠模拟器**：

- 通过硬件底层发信号，模拟出的输入更接近人手操作，**不留软件注入痕迹**；
- 在高敏感场景（如群内加好友）实测能降低被风控概率。

> 配合“控制频率、避免短时间批量操作”等规范用法，可获得更稳定的自动化体验。安全是工程问题，不是一句“零风险”的承诺。

## 快速开始（30 秒上手）

### 内嵌方式（.NET）

```bash
dotnet add package WeChatAuto4x.SDK
```

```csharp
var sp = WeAutomation.Initialize(o => o.EnableOCR = true);
using var factory = sp.GetRequiredService<WeChatClientFactory>();
var client = factory.GetWeChatClient("你的微信名");
await client.SendMessage("好友昵称", "hello world!");
```

### HTTP WebAPI 方式

```bash
# 启动 Server 后，任何语言都能调用
curl http://localhost:5000/api/v1/clients

curl -X POST http://localhost:5000/api/v1/clients/<clientId>/messages/send \
  -H "Content-Type: application/json" \
  -d '{"who": "好友昵称", "message": "你好"}'
```

更多接口与字段见 [HTTP 服务使用说明](httpserveruse.md) 与 [中间表字段说明](schema.md)。
